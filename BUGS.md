# Баг-репорты — Задание 2.1 (API)

**Окружение:** `https://qa-internship.avito.com` (общий тестовый стенд). Все баги воспроизводимы и подтверждены автотестами (указан связанный тест). Автотесты, выявляющие дефект, падают с сообщением, содержащим ID бага.

**Принятые обозначения:** *Серьёзность* (Severity) — насколько дефект ломает продукт (P0 — критический, P1 — высокий, P2 — средний, P3 — низкий). *Приоритет* (Priority) — в какой очереди исправлять: Срочно / Высокий / Средний / Низкий.

---

## BUG-01. Сервис принимает объявление с отрицательной ценой

**Серьёзность:** P1 (высокий) — нарушена валидация бизнес-данных, в системе появляются объявления с некорректной ценой.

**Приоритет:** Высокий — искажение цен напрямую влияет на витрину и сделки.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя, получить bearer-токен.
2. Отправить `POST /api/1/item` с телом:
   ```json
   {"sellerID": <id пользователя>, "name": "item", "price": -100,
    "statistics": {"likes": 1, "viewCount": 2, "contacts": 3}}
   ```

**Фактический результат:** код 200, объявление создано (`{"status": "Сохранили объявление - <UUID>"}`), отрицательная цена сохраняется и возвращается при чтении.

**Ожидаемый результат:** код 400, объявление не создано. Цена не может быть отрицательной; при этом граничное значение `price: 0` сервис корректно отклоняет, что подтверждает противоречие в валидации.

**Автотест:** `tests/test_item_api.py::TestItemAPI::test_create_item_negative_price`

## BUG-02. Сервис принимает объявление с отрицательными значениями статистики

**Серьёзность:** P2 (средний) — лайки/просмотры/контакты по смыслу неотрицательны; некорректные данные попадают в выдачу статистики.

**Приоритет:** Средний — на основной сценарий не влияет, но портит аналитику.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя, получить bearer-токен.
2. Отправить `POST /api/1/item` с телом:
   ```json
   {"sellerID": <id пользователя>, "name": "item", "price": 100,
    "statistics": {"likes": -1, "viewCount": -2, "contacts": -3}}
   ```

**Фактический результат:** код 200, объявление создано; `GET /api/1/statistic/{id}` возвращает отрицательные значения.

**Ожидаемый результат:** код 400, объявление не создано.

**Автотест:** `tests/test_item_api.py::TestItemAPI::test_create_item_negative_statistics`

## BUG-03. Любой авторизованный пользователь может удалить чужое объявление

**Серьёзность:** P0 (критический) — отсутствует проверка владельца ресурса при удалении, возможна порча данных любого продавца.

**Приоритет:** Срочно — уязвимость контроля доступа, позволяет массово удалять чужие объявления.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя A, получить его токен, создать объявление (`POST /api/1/item`), запомнить UUID.
2. Зарегистрировать пользователя B, получить его токен.
3. Отправить `DELETE /api/2/item/{UUID}` **с токеном пользователя B**.
4. Запросить `GET /api/1/item/{UUID}` с токеном пользователя A.

**Фактический результат:** шаг 3 — код 200; шаг 4 — код 404 (объявление действительно удалено чужим пользователем).

**Ожидаемый результат:** шаг 3 — код 401 или 403; объявление остаётся доступным (шаг 4 — код 200).

**Автотест:** `tests/test_item_api.py::TestItemAPI::test_delete_item_of_another_user_forbidden`

## BUG-04. При удалении несуществующего объявления тело ответа противоречит HTTP-коду

**Серьёзность:** P3 (низкий) — несоответствие контракту, вводит в заблуждение потребителей API.

**Приоритет:** Низкий — функционал не ломается, влияет только на обработку ошибок клиентами.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя, получить bearer-токен.
2. Отправить `DELETE /api/2/item/{случайный UUID}`.

**Фактический результат:** HTTP-код 404, но тело ответа содержит `"status": "500"` и пустое `message`:
```json
{"result": {"message": "", "messages": null}, "status": "500"}
```

**Ожидаемый результат:** HTTP-код и поле `status` в теле совпадают (404), `message` содержит описание ошибки, как у других 404-ответов сервиса.

**Автотест:** `tests/test_item_api.py::TestItemAPI::test_delete_item_not_found_response_body`

## BUG-05. Статистика остаётся доступной после удаления объявления

**Серьёзность:** P2 (средний) — в системе остаются «осиротевшие» данные: объявление удалено, а его статистика читается.

**Приоритет:** Средний — пользователю не мешает, но накапливает мусорные данные и расходует хранилище.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя, получить токен, создать объявление, запомнить UUID.
2. Удалить объявление (`DELETE /api/2/item/{UUID}`, код 200).
3. Убедиться, что `GET /api/1/item/{UUID}` возвращает 404.
4. Отправить `GET /api/1/statistic/{UUID}` и `GET /api/2/statistic/{UUID}`.

**Фактический результат:** обе версии статистики возвращают код 200 и данные удалённого объявления.

**Ожидаемый результат:** код 404 — статистика несуществующего объявления недоступна (как и для случайного UUID).

**Автотесты:** `tests/test_statistic_api.py::TestStatisticAPI::test_get_statistic_after_item_deleted[v1]`, `[v2]`

## BUG-06. Ручка статистики v2 на невалидный формат id отвечает 404 вместо 400

**Серьёзность:** P3 (низкий) — несогласованное поведение версий API и противоречие HTTP-кода телу ответа.

**Приоритет:** Низкий — косметика контракта.

**Шаги воспроизведения:**
1. Зарегистрировать пользователя, получить bearer-токен.
2. Отправить `GET /api/2/statistic/not-a-uuid`.
3. Для сравнения отправить `GET /api/1/statistic/not-a-uuid`.

**Фактический результат:** v2 — HTTP-код **404** при теле `{"result": {"message": "Неверный идентификатор статистики", ...}, "status": "400"}`; v1 — HTTP-код 400 с таким же телом.

**Ожидаемый результат:** обе версии возвращают HTTP-код 400, как зафиксировано в теле ответа и в поведении v1.

**Автотест:** `tests/test_statistic_api.py::TestStatisticAPI::test_get_statistic_invalid_format[v2]`

## BUG-07. Вводящее в заблуждение сообщение `invalid JSON body` при ошибках валидации

**Серьёзность:** P3 (низкий) — текст ошибки не соответствует причине отказа, усложняет интеграцию и отладку.

**Приоритет:** Низкий — влияет только на удобство поддержания API.

**Шаги воспроизведения:**
1. Отправить `POST /api/1/register` с валидным JSON, но нарушающим правила валидации, например `{"username": "ab", "password": "valid-pass-1"}` (username короче 3 символов).
2. Отправить `POST /api/1/autorize` с валидным JSON и паролем короче 8 символов.

**Фактический результат:** код 400 с телом `{"error": "invalid JSON body"}` — хотя тело запроса является корректным JSON и проблема в значениях полей.

**Ожидаемый результат:** сообщение описывает реальную причину отказа (например, «username должен содержать минимум 3 символа»).

**Примечание:** выявлено при ручном исследовании API; в автотестах проверяется только код 400, текст ошибки не assert'ится.
