# Промпты, использованные при работе с ИИ

При выполнении задания 2.1 использовался ИИ-ассистент (OpenCode, модель Kimi K3). Ниже — содержательная часть промптов и выжимка ответов (без секретов и токенов).

## Промпт 1 — ревью фреймворка

> Ты как инженер по автоматизации тестирования должен помочь мне сделать фреймворк и важно сделать его очень качественно, в файле qa-trainee-assignment-autumn-2026 описание задачи 2.1, я возьмусь за тестирование API, необходимо соблюдать чистоту архитектуры, паттерн Client Wrapper (Аналог POM, но для API), повторяющиеся коды выноси в отдельный файл как utils, чтобы не засорять основной код со вспомогательными функциями.
>
> 1. Проверь, что у меня корректно описаны модели для DTO из коллекции постмана
> 2. Проверь, что мой код соответствует архитектуре, чистоте кода, понятные комментарии у меня, чтобы любой разработчик и тестировщик понял его
> 3. Проверь на наличие лишних импортов
> 4. Проверь, что все шаги имею описание шагов для allure
>
> Вручную самостоятельно протестируй API и сверь мое решение, подскажи насколько покрыт функционал API тестами моими, какие еще сценарии сложные (маловозможные) есть?

### Ответ

**1. DTO-модели vs Postman-коллекция** — корректны:

| Коллекция | Модель | Статус |
|---|---|---|
| register → `{id, username}` | `RegisterResponse` | ✅ |
| autorize → `{accessToken, tokenType}` | `AutorizeResponse` | ✅ |
| POST item ← `{sellerID, name, price, statistics{likes, viewCount, contacts}}` | `ItemCreateRequest` + `Statistics` | ✅ |
| GET item → `[{id, sellerId, name, price, createdAt, statistics}]` | `Item` | ✅ |
| POST item → `{status: "Сохранили объявление - <UUID>"}` | `ItemCreateResponse` | ✅ |
| Ошибки item-ручек → `{result: {message, messages}, status}` | `ApiErrorResponse` | ✅ |

Важный нюанс учтён: в запросе поле `sellerID`, а в ответе `sellerId` — асимметрия API отражена в моделях правильно. Предложено добавить `Field(description=...)` и валидаторы (например, `price: int = Field(gt=0)`) в позитивные билдеры.

**2. Архитектура и чистота кода.** Client Wrapper соблюдён: `BaseClient` (сессия/токен/ретраи) → `AuthClient`/`ItemClient`/`StatisticClient`; слои не перемешаны — тесты не знают про `requests`, клиенты не знают про assert'ы. Комментарии поясняют «почему», а не «что». Рекомендация: указывать в docstring методов возможные коды ответов.

**3. Лишние импорты.** Чисто: `flake8` (правило F401) — 0 ошибок; единственный случай (`build_register_payload` в `test_autorize_api.py`) найден и убран.

**4. Allure-шаги.** `@allure.feature/story/title` есть везде, явные `@allure.step` — только в E2E. Предложение: повесить `@allure.step("POST /api/1/item")` на методы клиентов, чтобы шаги запросов попадали в отчёт без дублирования.

**5. Покрытие (~90%) и сложные сценарии на добавление:**

- Битый JSON (синтаксически) и запрос без `Content-Type: application/json` → ожидаем 400
- Переполнение типов: `price = 2^63`, огромные значения статистики
- Security-smoke: SQL-инъекция и XSS-строки в `name`, эмодзи/Unicode, имя в 10 000 символов
- Протокольные: `PUT /api/1/item` → 405; trailing slash `/api/1/item/`; пустой `Bearer `
- Нефункциональные: время ответа < N сек; `Content-Type: application/json` в ответах
- Спорное поведение для уточнения требований: username с пробелами/кириллицей регистрируется (201) — фича или баг?

## Промпт 2 — компактный формат таблицы TESTCASES.md

> Создай мне пример таблицы в TESTCASES.md, формат, которого не занимает так много строк кода как в TASK_1_BUGS.md

### Ответ

В `TASK_1_BUGS.md` используется HTML-формат «таблица на каждый баг» (~30 строк на баг). Предложен компактный формат: одна markdown-таблица на раздел, одна строка = один тест-кей:

```markdown
## Регистрация — POST /api/1/register

| ID | Название | Предусловия | Шаги | Ожидаемый результат | Приоритет |
|----|----------|-------------|------|---------------------|-----------|
| TC-REG-01 | Успешная регистрация | — | POST /register {username, password} — валидные | 201; тело: id (int>0), username = из запроса | High |
| TC-REG-02 | Дубликат username | Пользователь создан | POST /register с тем же username | 409; поле error | High |
| TC-REG-03 | Граница: username 2 символа | — | POST /register {username: "ab", ...} | 400 | Medium |
| TC-REG-04 | Граница: username 3 символа | — | POST /register {username: 3 символа, ...} | 201 | Medium |
```

Плюсы формата: плотность (4 кейса = 4 строки), читаемые diff'ы в git, обзорность раздела, нативный рендеринг на GitHub. Нюансы: многошаговые шаги писать через `→`, многострочность в ячейке через `<br>`, критерий перехода к развёрнутому формату — ячейка длиннее ~150 символов.

## Промпт 3 — переоформление BUGS.md

> Переоформи мне BUGS.md в более приятный вид

### Ответ

Проблема текущего вида — нет быстрого обзора. Предложен гибридный формат: сводная таблица вверху + детали по единому шаблону ниже.

Сводная таблица:

```markdown
| ID | Дефект | Серьёзность | Приоритет | Ручка | Автотест |
|----|--------|:-----------:|:---------:|-------|----------|
| BUG-01 | Принимается отрицательная цена | P1 | Высокий | POST /api/1/item | ✅ |
| BUG-02 | Принимается отрицательная статистика | P2 | Средний | POST /api/1/item | ✅ |
| BUG-03 | Можно удалить чужое объявление | P0 | Срочно | DELETE /api/2/item/{id} | ✅ |
| BUG-04 | Тело 404-ответа содержит "status": "500" | P3 | Низкий | DELETE /api/2/item/{id} | ✅ |
| BUG-05 | Статистика жива после удаления объявления | P2 | Средний | GET /api/{v}/statistic/{id} | ✅ |
| BUG-06 | v2 статистики: 404 вместо 400 на кривой id | P3 | Низкий | GET /api/2/statistic/{id} | ✅ |
| BUG-07 | Misleading "invalid JSON body" при валидации | P3 | Низкий | register / autorize | ручной |
```

Шаблон детального описания каждого бага:

```markdown
## BUG-03. Любой авторизованный пользователь может удалить чужое объявление

| | |
|---|---|
| **Серьёзность** | P0 (критический) |
| **Приоритет** | Срочно — уязвимость контроля доступа, блокер релиза |
| **Ручка** | `DELETE /api/2/item/{id}` |
| **Автотест** | `test_item_api.py::TestItemAPI::test_delete_item_of_another_user_forbidden` ❌ |

**Шаги:**
1. Пользователь A: регистрация → токен → создание объявления, запомнить UUID
2. Пользователь B: регистрация → токен
3. B отправляет `DELETE /api/2/item/{UUID}` со своим токеном
4. A запрашивает `GET /api/1/item/{UUID}`

**Фактический результат:** шаг 3 → 200, шаг 4 → 404 — объявление удалено чужим пользователем

**Ожидаемый результат:** шаг 3 → 401/403, объявление остаётся доступным
```

## Промпт 4 — написание тестов на основе TESTCASES.md

> На основе документов, составь мне тесты, описанные в TESTCASES.md, если в ходе написания тестов встречаются противоречивые ответы тестов - посмотри BUGS.md, есть ли там этот противоречивый тест-кейс, то оставь как описано в шагах тест-кейса, чтобы вопроизвести этот баг.

### Ответ

**Маппинг TESTCASES.md → тесты** (группа кейсов = тестовый класс, TC = тест/параметр):

| Раздел TESTCASES.md | Файл тестов |
|---|---|
| 1. Регистрация (TC-REG-01…13) | `tests/test_register_api.py` |
| 2. Авторизация (TC-AUTH-01…05) | `tests/test_autorize_api.py` |
| 3–6. Объявления (TC-CREATE/GET/SELLER/DEL) | `tests/test_item_api.py` |
| 7. Статистика (TC-STAT-01…07) | `tests/test_statistic_api.py` |
| 8. E2E (TC-E2E-01) | `tests/test_e2e.py` |

Ожидаемые результаты берутся из колонки «Ожидаемый результат» — тест кодирует правильное поведение, а не текущее поведение сервиса.

**Обработка противоречий.** Если фактический ответ расходится с ожиданием из тест-кейса: проверяю BUGS.md; если расхождение задокументировано — тест остаётся с ожиданием из тест-кейса (падает и воспроизводит баг), а в assert добавляется ссылка:

```python
assert response.status_code == 400, (
    "BUG-01 (BUGS.md): сервис принял объявление с отрицательной ценой. "
    f"Ожидали 400, получили {response.status_code}. Ответ: {response.text}"
)
```

Нюанс: если из-за бага объявление всё-таки создалось, оно удаляется через `cleanup_item_if_created()` — общий стенд не засоряется.

**Итог:** 62 теста покрывают все 40+ кейсов; 55 passed / 7 failed, все падения — задокументированные противоречия (BUG-01…BUG-06); ни одного «сломанного» теста.
